## 2026-08-29: 本番を ConoHa VPS → 自宅ミニPC へ移設、公開方式を Cloudflare Tunnel + 共有Caddy に変更

**決定**: `novelshelf.jp` の本番を ConoHa VPS（`163.44.116.137`）から自宅ミニPC（GMKtec M5 Ultra / Ryzen 7 7730U / 32GB / 1TB NVMe、Ubuntu Server 24.04 LTS）へ移設する。`Personal_AI_Secretary-project` と同一機に同居させる。外部公開はポート開放ではなく **Cloudflare Tunnel**、リバースプロキシは AI Secretary と共有する **Caddy 1枚**（`/srv/edge/`）に集約し、NovelShelf 自前の `nginx` + `certbot` は廃止する。

**背景・理由**:
- 自宅回線は au系（KDDI）光で **CGNATではない**が、二重NAT（HGW → 親機ルーター → Wi-Fi中継器）＋動的IPv4。ポート開放だと「ルーターのブリッジ化」「DDNS」「HGWでのポート転送」が必要。Cloudflare Tunnel は**外向き接続のみ**で成立し、これらすべて不要（CGNAT/DS-Lite/MAP-E/二重NATのいずれでも動く）
- TLS は Cloudflare がエッジで終端 → ミニPCに証明書を置かない（Let's Encrypt / certbot 不要）
- AI Secretary の設計（`Personal_AI_Secretary-project/docs/deployment.md`）が既に Caddy 採用。静的2サービスの Host 振り分けに Traefik はオーバースペック、Nginx は手書きコスト高 → Caddy に統一
- ドメインの DNS は Cloudflare へ移管が前提（`cfargotunnel.com` へのプロキシCNAMEは Cloudflare 権威DNSでしか機能しない）。`novelshelf.jp` はムームードメイン登録のまま、ネームサーバーのみ Cloudflare へ

**データ移設**: 永続データは Postgres の `postgres_data` ボリュームに全て入っており（小説本文もファイル保存なし）、`pg_dump -Fc` → リストアで移設できる。利用者は本人のみのため 30分程度のメンテ窓でよい。手順は [`MIGRATION_to_minipc.md`](MIGRATION_to_minipc.md)。段階的解約（T0カットオーバー → T+7d でVPSアプリ停止・最終ダンプ → restic 実証後 T+21d で ConoHa 解約、DNSロールバック可能な状態を維持）。

**必要な変更**:
- `docker/docker-compose.minipc.yml` を新規作成（`nginx`/`certbot` を含まず、外部ネットワーク `edge` に `novelshelf-frontend`/`novelshelf-backend` エイリアスで参加、`ports: !reset []`）。`docker-compose.prod.yml`（VPS用）は当面残置（VPS復帰用）
- フロントの「全話をオフライン保存」を**クライアント分割方式へ改修**（下記別項）
- `DEPLOY.md` は移設後に「旧VPS手順（アーカイブ）」へ位置づけ変更、再デプロイ手順をミニPC版へ

**採用しなかった案**: (a) ポート開放 + DDNS → 二重NAT解消と MAP-E 懸念、IP変動対応が増える。(b) 物理ボリュームコピーでの移設 → 速いが `POSTGRES_PASSWORD` 一致必須・破損をそのまま運ぶ・バージョン差に弱いため代替案どまり。(c) NovelShelf を VPS に残す → AI Secretary と別ホストになりリバプロを2枚維持することになる。

## 2026-08-29: 全話一括ダウンロード（`/download`）を Cloudflare 100秒制限のためクライアント分割方式へ改修（予定）

**問題**: `POST /api/v1/novels/{novelId}/download`（`NovelController#downloadAll` → `NovelQueryService#getAllChapterContents`）は**完全な同期処理**で、全話をソースサイトから毎回取得し直し、`NarouRateLimiter` が1秒間隔を強制するため 300話で約5分（コード内コメント）。Cloudflare Tunnel 経由になると、Cloudflare の Free/Pro/Business プランは**オリジン応答が約100秒を超えると 524 エラー**で切断する（Enterpriseのみ延長可）。→ 90話前後が境界。なろう長編は数百〜数千話が普通なので、移設後に多くの作品で 524 になる。Caddy の `read_timeout` 延長では回避できない（100秒制限は Cloudflare エッジ〜オリジン間の話）。

**決定**: フロントの `downloadAll()`（`frontend/src/app/(protected)/(shell)/novels/[novelId]/page.tsx`）を、「`POST /novels/{id}/download` 一括」から「`GET /novels/{id}/chapters` で一覧 → 各話 `GET /api/v1/chapters/{chapterId}/content` を順次取得 → `putCachedChapter` → 進捗表示」へ変更する。1リクエストは数秒で完結し 100秒制限に当たらない。合計時間は同じ（サーバー側レートリミッタが律速）だが進捗表示が自然になり中断/再開もしやすい。**バックエンドは既存エンドポイントのみで変更不要**。将来的に `POST /novels/{id}/download` と `getAllChapterContents` は廃止候補。

**移設前に実施**: 本棚の最大話数の作品で現VPSへ直接 `POST /download` を実測（`ミニPC-Linux移行手順.md` 9-3 の T1〜T4）。`>=90s` または長編追加予定なら改修してから移設。

**採用しなかった案**: バックエンドを `application/x-ndjson` ストリーミング応答にする案 → 1リクエストのまま回避できる可能性が高いが、バックエンド＋フロント両方の改修が必要で分割方式より複雑。

## 2026-08-18: Playwright E2Eジョブの失敗原因を修正（テストの陳腐化が2件）

**経緯**: 上記のgradlew権限修正後もCIは通ったが、`e2e-live.yml`の「Playwright E2E」ジョブは
別原因で毎回失敗し続けていた。Docker Desktopを起動してローカルで`e2e-live.yml`と同じ手順
（`docker compose up --build` → `npm run test:e2e`）を再現し、原因を特定・修正した。
`critical-journey.spec.ts`は初回コミット(2026-07-19)からほぼ一度も通しで成功したことが
なかった可能性が高い（後述の2つの原因がいずれも同日か近い時期に生まれた機能に起因するため）。

**原因1: 「作品を追加」ダイアログのURL欄のplaceholderテキストが古いまま**。テストは
`"https://ncode.syosetu.com/xxxxxx/"`というplaceholderを探していたが、実際のUIは
クリップボード自動読取機能の追加(`a9624e9`、2026-07-19)で
`"URLを貼り付け、または空欄のまま「追加」でコピー済みURLを使用"`に変わっていた。
テスト側のロケータを現在の文言に更新。

**原因2: 読書画面のヘッダー/フッター（Aaボタン・次の話ボタン等）はイマーシブ表示**
（`chromeVisible`、既定は非表示、本文タップで表示切替、話を切り替えるたびに非表示へリセット）
**になっており、テストは本文をタップせずいきなりAaボタンをクリックしようとして
「element is outside of the viewport」で失敗していた**。これはCSSの`transform: translateY(...)`
でヘッダー/フッターを画面外にスライドさせる実装のため、Playwrightが「スクロールして
表示領域内に入れる」処理を試みても原理的に届かない（transform後の見た目の位置はスクロールでは
変わらないため）。修正: フォント設定操作の前に`page.locator("article").click()`で本文中央付近を
一度タップしてイマーシブ表示を出してからAaボタンを操作するようにテストを変更。

**原因3（軽微、非ブロッカー）**: `第1話 / 15話`のように総話数を固定値でハードコードしていたが、
テスト対象のなろう実作品は運用期間中に実際に15話→46話へ増えていた（連載中作品への実アクセスを
伴うライブテストである以上、当然変わりうる）。総数を検証する意味は薄いため、
`/第1話 \/ \d+話/`のような正規表現に緩め、話数そのものではなく話番号の遷移(1→2)のみを検証する
形にした。

**結論**: 3件とも本番のバグではなく、テストコード側が実装の変更（クリップボード機能追加、
イマーシブ表示追加、外部サイトの実データ変化）に追随できていなかったことが原因。修正後、
ローカルで`npm run test:e2e`が成功することを確認済み（1 passed）。

## 2026-08-18: バックエンドCIが初回コミット以来ずっと失敗していたことが判明・修正

**インシデント**: ユーザーが「なろう疎通確認」ワークフロー（週次cron）の失敗通知メールに気づき調査を依頼。調べたところ、この週次ワークフローだけでなく**通常のCI（`ci.yml`のbackendジョブ）も、2026-07-19の初回コミット以来、直近まで15回以上連続で失敗し続けていた**ことが判明した。デプロイは手動SSH+`docker compose`でCIの成否に依存しないため、誰も気づかずに1ヶ月近く放置されていた。

**原因**: `backend/gradlew`がGitに実行権限なし（モード`100644`）のまま記録されていた。Windows環境からの初回コミットで実行ビットが正しく記録されなかったのが原因。素のUbuntuランナー上で`./gradlew`を直接実行するジョブ（`ci.yml`のbackendビルド、`e2e-live.yml`の`narou-live-check`）は`Permission denied`で即座に失敗する。一方、本番デプロイ経路（`docker/backend/Dockerfile`）は`RUN chmod +x gradlew`を明示していたため影響を受けず、**本番(`novelshelf.jp`)には影響なし**。`e2e-live.yml`のもう一方のジョブ（Playwright E2E、Docker Compose経由）も同じ理由で影響を受けていないが、これは別原因（`npm run test:e2e`失敗）で毎回失敗しており、原因は別途調査中。

**修正**: `git update-index --chmod=+x backend/gradlew`でGit側の実行ビットを修正。加えて`ci.yml`・`e2e-live.yml`の該当ステップに`chmod +x gradlew &&`を追記し、将来また実行ビットが失われても壊れないようにする防御的対応も実施（Dockerfileと同じ考え方）。

**教訓**: デプロイがCIの成否をゲートしない運用では、CI失敗に気づく手段がメール通知頼みになる。今後、新しいワークフロー・スクリプトファイル（特にWindows環境で作成したシェルスクリプト等）を追加した際は、Gitのファイルモード（`git ls-files -s`で確認できる。実行可能なら`100755`）を確認する習慣をつける。

## 2026-08-16: なろう目次のページネーション対応、話一覧への「章」グループ表示

**①なろうの話一覧が100話超で2ページ目以降を取りこぼす不具合を修正**: `NarouAdapter.fetchChapterList`は目次ページの1ページ目（`https://.../{ncode}/`）しか取得しておらず、100話を超える長編（目次が`?p=2`以降にページングされる）は101話目以降が本棚に一切表示されなかった（ユーザー報告の実例: `novel18.syosetu.com/n7982ej/`、全194話中101〜194話目が欠落）。修正: 目次ページ下部の「次へ」ページャ（`a.c-pager__item--next`）を、それが`<a>`でなくなる（＝最終ページに達し同クラスの`<span>`に変わりリンクを持たなくなる）まで辿り、各ページの話を1つのリストに積み上げるようにした。ユーザーは従来どおり1ページ目のURL（作品トップページ）を登録するだけで全話（何ページ目に渡っていても）が取り込まれる。無限ループの保険として最大100ページ（=10,000話相当）でループを打ち切るガードを追加。

**②なろう・カクヨムの話一覧の「章」グループ分けをアプリ側にも反映**: 両サイトとも、作者が話を「第一章」のような章単位でグループ分けしている場合がある（なろうはHTML上`p-eplist__chapter-title`要素、カクヨムは`__NEXT_DATA__`内Apollo正規化キャッシュの`TableOfContentsChapter.chapter.title`）。従来はこの章題を無視して話だけをフラットなリストとして取り込んでいた。`ExternalChapter`・`Chapter`エンティティ（DBカラム`arc_title`、`V8__chapter_arc_title.sql`）・`ChapterResponse`に`arcTitle`（章分けが無い作品・サイトではnull）を追加し、作品詳細画面の話一覧で、直前の話と`arcTitle`が変わるたびに章題を見出しとして表示するようにした（`novels/[novelId]/page.tsx`）。ハーメルンは目次テーブルに章グループ分けの仕組みがあるか実機確認できなかったため、`HamelnAdapter`は当面`arcTitle`を常にnullで返す（将来ユーザーから実例があれば対応）。

**採用しなかった案**: 章を`chapters`テーブルとは別の中間テーブル（`arcs`）として正規化する案 → 章は「話が属するグループの題名」という文字列以上の実体（並び順や独自メタデータの管理等）を今のところ持たないため、`Chapter`に非正規化した`arcTitle`列を持たせるだけで要件を満たせると判断し、過剰設計を避けた。

## 2026-07-26（続き）: 「追加順」ソートの不具合修正・本棚検索へのサイト別フィルター追加

**⑤「追加順」で並び替えても最後に追加した作品が一番上に来ない不具合を修正**: `BookshelfController.list()`は`sort=recent`のときだけ`lastReadAt`基準でソートし、`groupBy`指定時だけ`groupComparator`でソートしていたが、**「追加順」（`sort`も`groupBy`も未指定の既定ケース）にはソート処理が一切無かった**。`BookshelfEntryRepository`のJPQLクエリにも`ORDER BY`が無いため、返る順序はDBの内部フェッチ順（挿入順とは限らず、`LEFT JOIN FETCH`+`DISTINCT`のせいで特に不安定）に委ねられていた。「追加順」を選んでも新しく追加した作品が末尾やランダムな位置に出ることがあったのはこれが原因。修正: 既定ケースでも`addedAt`降順で明示的にソートするようにした（`groupComparator`のデフォルトケースと同じ式）。回帰テスト`BookshelfControllerTest`（DBフェッチ順をわざと追加順と異なる並びにしても、レスポンスは正しくaddedAt降順になることを確認）を追加。

**⑥本棚の検索フィルターにサイト別の絞り込みを追加**: ②で作った小説名フィルターに、`/search`画面で使っていたのと同じサイトチップ（すべてのサイト/なろう/カクヨム/ハーメルン）を追加した。`sitesApi.list()`を`(shell)/page.tsx`で新たに呼び出し（既存の他画面と同じパターン）、`entries`に対してクライアント側で`novel.site === siteFilter`によるAND条件フィルタを適用する。追加のバックエンドAPI呼び出しは発生しない。

## 2026-07-26: ユーザー報告3件の対応（本棚追加時のタイトル欠落・検索機能の作り直し・読書画面のお気に入り）

**③読書画面からお気に入り登録できるようにする**: これまでお気に入りのトグルは本棚画面の各行のハートアイコンからのみ可能で、読書画面（チャプター表示画面）には無かった。読書画面のヘッダー（イマーシブ表示、本文タップで表示）に本棚画面と同じハートアイコンを追加し、その場でお気に入りのON/OFFを切り替えられるようにした。読書画面は`novelId`のみを持ち`shelfEntry`のIDを持たないため、`shelfApi.list()`を呼んで`novelId`が一致するエントリを探す方式にした（作品詳細画面の既存パターンを踏襲）。

## 2026-07-19: ハーメルンR18サイト（h.syosetu.org）に対応

**決定**: `HamelnAdapter`がR18作品のURL（`h.syosetu.org`）を通常サイト（`syosetu.org`）と誤って同一視し、常に通常サイトのURLで本文取得を試みて失敗する不具合をユーザー報告により発見・修正した。なろうのR18対応（`novel18.syosetu.com`）と同じパターンで、`HamelnProperties`に`r18SiteBaseUrl`を追加し、URL/externalNovelIdからR18判定（`h.syosetu.org`ホスト、または`"r18:"`プレフィックス）を行った上で正しいサイトへリクエストするよう修正した。

**追加で判明した問題**: `h.syosetu.org`は年齢確認クッキー（`over18=off`、実機確認で判明した値）が無いと年齢確認ページにリダイレクトされ、本文取得に失敗する（なろうR18の`over18=yes`と似た仕組みだが値が異なる）。`fetchHtml`で常にこのクッキーを付与するよう修正（通常サイト側では無視されるだけなので分岐不要、なろうと同じ方針）。

**動作確認**: 実際に`h.syosetu.org`へアクセスして年齢確認ページの存在と、`?cookie_set=r18`リンクで得られる`Set-Cookie: over18=off`を確認した上で、実在するR18作品（本文取得まで）に対する疎通テスト（`HamelnAdapterLiveTest`に追加、`-DhamelnR18NovelId=<id>`で手動実行）で確認済み。

## 2026-07-19: モバイルを「アプリらしい」固定画面にする（バウンス・意図しないズームの抑止）＋読書画面の導線改善

**決定**: ユーザーからスマホでの操作感についてまとめて要望を受け、以下を対応した。

1. **スクロールバウンス・意図しないズームの抑止**:
   - `viewport`に`maximumScale: 1, userScalable: false`を追加し、ピンチ/ダブルタップズームを無効化した。文字サイズの調整は既存の設定画面のフォントサイズ機能で行える（ブラウザのズームに頼らない設計とした）。
   - `html`/`body`に`overscroll-behavior-y: none`を追加し、ページ全体のラバーバンドバウンスが伝播しないようにした。読書画面の本文等、個別にスクロール可能な内部コンテナのスクロールは影響を受けない。
   - iOS Safariは`input`/`select`/`textarea`の実効フォントサイズが16px未満だとフォーカス時に自動でページ全体をズームする仕様のため、モバイル幅（767px以下）ではフォーム要素のフォントサイズを16px以上に強制する`!important`ルールを追加した（デザイン上の`text-sm`等はTailwindのクラスとして残したまま、実効値だけ底上げする）。
   - `h-screen`/`min-h-screen`（`100vh`固定）を使っていた箇所（読書画面・認証画面・共有画面・シェルレイアウト）はすべて`h-dvh`/`min-h-dvh`（動的ビューポート高さ）に置き換えた。モバイルブラウザのアドレスバーの表示/非表示で可視領域が変わっても、レイアウトが飛ばなくなる。「上下スクロールで画面が動く」という報告の主因はこれだと判断した。

2. **読書画面の導線改善**（ユーザー指定）:
   - フッターの「前の話」「次の話」ボタンの左右位置を入れ替え（次の話を左、前の話を右に）。各ボタン内のアイコンの向きはそのまま（次の話は右矢印、前の話は左矢印）で、位置だけを入れ替えた。
   - 「話一覧」リンクをフッター中央からヘッダー右側（「Aa」設定ボタンの隣）に移動した。
   - 本文の最後までスクロールした状態で、さらに一定時間（400ms超）スクロール操作が続いた場合に次の話へ自動遷移する機能を追加した。「最後に到達した瞬間」ではなく「そこからさらに操作が続く」ことを条件にすることで、最終行を読み終えた直後に意図せず次の話へ飛ぶことを防いでいる。

**動作確認**: Playwright（iPhone 13エミュレーション）で、viewport metaの内容、フォーム要素の実効フォントサイズ（16px）、`overscroll-behavior-y`の適用、ヘッダー/フッターのボタン配置、実際に本文末尾への繰り返しスクロールで次の話へ遷移すること、をすべて確認した。

## 2026-07-19: パスワードリセット機能をSMTPプロバイダ非依存で実装

**決定**: SMTP送信方式（Gmail SMTP / SendGrid・AWS SES等 / ConoHaメール）をユーザーが未決定のまま、`spring-boot-starter-mail`（`JavaMailSender`）でホスト・ポート・ユーザー名・パスワードを環境変数（`MAIL_HOST`/`MAIL_PORT`/`MAIL_USERNAME`/`MAIL_PASSWORD`/`MAIL_FROM`）から受け取る汎用実装で機能を作り切った。どのプロバイダもSMTPプロトコルで送信できるため、コード変更なしに`.env`へ接続情報を設定するだけで動く。未設定（空文字）のままでもアプリは起動でき、送信は失敗するだけで呼び出し元には伝播しない（`PasswordResetService`参照）。

**設計**: `refresh_tokens`と同じ「生トークンは発行時のみ、DBにはハッシュのみ保存」方式（`RefreshTokenGenerator`を流用）。パスワードリセット要求は、対象メールアドレスが実在するかどうかに関わらず常に同じレスポンス（204）を返し、実在する場合のみ内部でトークン発行・メール送信を行う（アカウント存在の推測を防ぐ）。リセット成功後は当該ユーザーの全リフレッシュトークンを失効させる（パスワード漏えい時の対策として一般的な慣行）。トークンの有効期限は30分（`PASSWORD_RESET_TTL_MINUTES`で変更可）。

**動作確認**: MailHog（使い捨てのDockerコンテナ、本番構成には含めない）をSMTP送信先に一時的に差し替え、実際にメールが送信されること、メール内のリンクから実際にパスワードを再設定できること、旧パスワードが失効し新パスワードでログインできることをPlaywrightで実際にブラウザ操作して確認した。

**採用しなかった案**: プロバイダを先に決めてから実装する案 → SMTPという共通プロトコルの上に薄い設定層を作るだけで済むため、プロバイダ選定を待つ理由がないと判断した。

**インシデント（本番障害、2026-07-19）**: この機能を本番デプロイした直後、サイト全体が数分間ダウンした。`spring-boot-starter-mail`が自動追加する`MailHealthIndicator`が`/actuator/health`の一部としてSMTP接続テストを行うが、`MAIL_HOST`未設定（ユーザーがまだプロバイダを決めていないため、想定どおりの状態）だとこのテストが失敗し、health全体がDOWNになった。Dockerの`healthcheck`（`curl -f .../actuator/health`）がこれを検知して`backend`コンテナを「unhealthy」と判定し、`nginx`は`depends_on: backend healthy`のため起動できず、サイト全体（`https://novelshelf.jp`）が応答しなくなった。開発機のローカルDocker環境ではこのヘルスチェックの詳細を確認しておらず、実際にデプロイして初めて気づいた。`management.health.mail.enabled: false`でメールの健全性を全体のhealthから切り離して解消（メール送信可否は`PasswordResetService`側で個別にハンドリング済みのため、アプリ全体の健全性とは無関係と判断）。**教訓**: 新しい依存関係（特に`spring-boot-starter-*`系のautoconfigure）を追加する際は、それが`/actuator/health`に暗黙で寄与しないか確認すること。ローカルのdocker-compose環境でも`docker compose ps`でhealthy/unhealthyを確認してからデプロイする。

## 2026-07-19: カクヨム・ハーメルンに対応、pixiv小説は対応しない（規約調査の結果）

**決定**: ユーザーの依頼により、カクヨム・ハーメルンのrobots.txt/利用規約を調査した上で`KakuyomuAdapter`・`HamelnAdapter`を実装した。pixiv小説は明確な禁止規定があるため実装せず、リンクのみ登録（本文取得なし）のまま据え置く。

**調査結果の要点**:
- **カクヨム**: robots.txtは話本文ページ（`/works/*/episodes/*`、末尾が`/read`の別ルートを除く）へのアクセスを禁止しておらず、`ClaudeBot`向けに`Crawl-delay: 1`まで明示している。利用規約（`kakuyomu.jp/legal/tos`第12条）は「取得したデータを私的使用の範囲を超えて複製・販売・出版すること」を禁じているのみで、自動アクセス自体を禁じる条項はない。なろうと同水準のリスクと判断し実装。
- **ハーメルン**: robots.txtは汎用UAに対し話本文ページを禁止していない（SEO/広告系botのみ個別ブロック）。一方、利用規約（`syosetu.org/?mode=rule`）は「サイトに過度の負荷をかける行為」の例示に「ツール使用など」を挙げており、文言だけを見るとやや曖昧。ユーザーに調査結果を共有した上で、なろう・カクヨムと同じ低頻度・個人利用限定の方針（1秒間隔・読んでいる話のみ取得）であれば許容範囲と判断し、ユーザーの明示的な指示で実装した。
- **pixiv小説**: 公式ガイドラインに「クローラーなどのプログラムを使って作品等を収集する行為」を**目的を問わず**禁止する条項が明記されており、robots.txtでも`ClaudeBot`・`anthropic-ai`等をサイト全体で名指しブロックしている。タイトル・作者名のみの軽微な取得であっても「収集する行為」に該当しうると判断し、実装しないことをユーザーと合意した。リンクのみ登録し、タイトルはユーザーが手動編集する（[プレースホルダー作品のタイトル手動編集機能]参照）。

**実装方式**: 両サイトとも公式の開発者向けAPIが存在しないため、実際にブラウザが受け取るページのHTMLをそのまま取得する。カクヨムは作品ページに埋め込まれたNext.jsの`__NEXT_DATA__`（Apolloの正規化キャッシュ）を構造化データとして解析するため、なろうよりむしろ堅牢（話一覧もページング制約なく1回のリクエストで全件取得できる）。ハーメルンはschema.orgのmicrodata（`itemprop`属性）と`id="honbun"`/`id="maegaki"`/`id="atogaki"`という明確に分離されたIDを使っており、なろうで起きたような前書き取り違えのリスクは低い。両サイトともレート制限（1秒間隔）は個人利用の1ユーザーが読んでいる話を都度1件ずつ取得する用途に限定し、一括クロールは行わない（既存のなろう方針を踏襲）。

**実装中に発見した既存バグ**: `sites`テーブルの`is_supported`フラグ（`V2__seed_sites.sql`でカクヨム・ハーメルン・pixivとも`false`でシード）と、`NovelSiteAdapter.isSupported()`（アダプタBean側、常に`true`を返す設計）が別々の仕組みで、前者を更新し忘れると「作品の追加（`resolveNovel`）は成功するのに話一覧・本文取得だけ常に空になる」という気づきにくい不具合になることが判明した。`V4__support_kakuyomu_hameln.sql`で`is_supported`を`true`に更新して解消（pixivは`false`のまま）。今後同様に新サイト対応する際は、アダプタ実装だけでなくこのDBフラグも忘れずに更新すること。

**採用しなかった案**: ハーメルンも規約の曖昧さを理由に見送る案 → ユーザーが調査結果を踏まえた上で実装を希望したため採用しなかった。

## 2026-07-19: 縦書きリーダーのiPhone/Android横スクロール不具合を`ml-auto`で修正

**決定**: 縦書き表示のコンテナを`flex justify-end`ではなく`flex`+`article`側`ml-auto`に変更し、`overflow-auto`側の親にも`min-h-0`を追加した。

**理由**: `justify-content: flex-end`のflexコンテナは、はみ出た子要素がjustify-content開始方向（横書きモードのflexでは左）に隠れる形になり、多くのブラウザ（特にモバイルSafari/Chrome）でその隠れた部分がスクロール可能領域として認識されないというflexboxの既知の挙動が原因で、iPhone/Androidで縦書き話の横スクロールが一切できなくなっていた（ユーザー報告、2026-07-19）。`ml-auto`（コンテンツがはみ出ない場合だけ右寄せになり、はみ出た場合は通常のフロー幅を持つ）に変更することで解消。`min-h-0`は`flex-1`要素がデフォルトの`min-height: auto`により縦方向にも縮小できずレイアウトが崩れることがあるflexbox特有の問題への対策。iPhoneビューポート（Playwright, `devices["iPhone 13"]`）で実機相当の確認済み。

**背景**: 同時にユーザー報告のあった「小説取得時に前書きだけが本文として表示される」バグ（`NarouAdapter`が`div.p-novel__text`の最初の一致を本文として誤取得していた）も、前書き/あとがき用の修飾クラスを`:not()`で除外する形で修正済み。

## 2026-07-19: 読書画面のページ送り(pagination)を実装、ただし横書きのみ。縦書きは当面スクロール表示にフォールバック

**決定**: 上記の決定を受けて`pageMode: PAGINATION`の実際の表示を実装した。CSS多段組(`columns`)で本文を画面幅ぴったりの列に分割し、`scrollLeft`を列幅ぶんずつ動かしてページをめくる方式。ただし**横書き(HORIZONTAL)のみ**有効にし、**縦書き(VERTICAL)は`pageMode: PAGINATION`設定でも従来のスクロール表示にフォールバックする**（`isPaged`の判定に`settings.writingMode === "HORIZONTAL"`を追加）。

**理由**: 横書きは実機検証（Playwrightで文字ごとの`getClientRects()`を取得し、ページ境界をまたいで中途半端に見えている文字がないか自動チェック＋ズームスクリーンショットで目視確認）で複数の余白・フォントサイズ設定において完全にクリーンだった。一方、縦書き(`writing-mode: vertical-rl`)は下記の対策を段階的に施してもなお、一部のページ境界で文字が数px単位で視覚的に見切れる不具合が再現し続けた（ズームスクリーンショットで実際にグリフが欠けているのを確認済み）。

試した対策（いずれも部分的にしか効かなかった、またはズレの発生位置が変わるだけだった）:
1. `column-fill: auto`の明示指定（既定の`balance`は列の高さを均等化しようとして列幅の前提が崩れる列詰め方をするため）。
2. 幅の2パス測定（1パス目は`width`を指定せず自然なレイアウトで`scrollWidth`を測り、画面幅の整数倍に切り上げた値を2パス目で明示`width`として再指定し、総幅を強制的に画面幅の整数倍へ揃える）。
3. `columnWidth`を「1行の送り幅(`fontSize*lineHeight`)の整数倍」に切り下げる（縦書きは行送り単位でしかページ境界がずれないはずという仮説）。
4. `columnGap`を`画面幅-columnWidth`ではなく`2*実効パディング`から算出し直し、総幅のtelescoping計算（`padding*2 + N*columnWidth + (N-1)*columnGap = N*画面幅`）が正確に成立するよう補正。
5. `columnCount`も明示指定して列幅の「最適化による再配分」の余地を無くす。

いずれもHORIZONTALには不要（元々発生しない）で、VERTICALには効果が限定的だった。原因はCSS多段組と`vertical-rl`の組み合わせにおけるブラウザの内部レイアウト計算（サブピクセル丸め、または列と行送りの軸の解釈）がJS側からの予測と一致しない何らかの実装依存の挙動と推測されるが、根本原因の完全な特定には至っていない。

**次にやるなら**: JS側での事前計算に頼らず、実際にレンダリングされたDOM上の文字位置を実測してページ境界（`scrollLeft`の目標値）を決める方式（計算ではなく測定ベース）への作り直しが有力な次の一手。`docs/NEXT_TASK.md`に詳細を記載。

**採用しなかった案**: 縦書きも含めて全面的に妥協なく仕上げる案 → 原因未特定のまま時間を掛け続けるより、横書きだけでも実用可能な形で先に届け、縦書きは既存のスクロール体験（元々十分快適）を維持する方が個人利用として合理的と判断。

## 2026-07-19（続き）: 縦書きページ送りを「実測ベース」で再実装したが、依然として解消せず横書きのみに再度フォールバック

**決定**: 上記エントリの「次にやるなら」に記載した「実測ベース」方式（JS側の事前計算をやめ、実際にレンダリングされた各行の絶対x座標を`Range.getClientRects()`で直接測定し、行と行の間隔が明らかに広い場所＝本当のページ境界を検出してそこにscrollLeftを合わせる）を実装したが、それでもなお一部ページで文字の見切れが再現した。引き続き**縦書き+ページ送りは横書き専用のフォールバックのまま**とする。

**分かったこと**:
- 実測した行と行の間のx方向の間隔（デルタ）を全て集計したところ、**列(ページ)境界とみなされるべき箇所でも、通常の行間（約30〜31px）と比べて有意に大きいデルタが一切観測されなかった**（`column-gap`をどんな値に設定しても、実測される行位置のデルタに反映されていないように見える）。
- これは、Chromium（Playwright同梱）の`vertical-rl` + CSS多段組(`columns`)の組み合わせにおいて、`column-gap`が期待通りにレンダリングされていない（またはJS側から観測可能な形でレイアウトに反映されていない）可能性を示唆する、実装依存のブラウザ挙動と推測される。
- 併せて、前回のエントリの対策5「`columnCount`を明示指定」は、総幅のpinning自体は成立させても列数の算出元（当時のJS側予測値）が実際の列数とズレていた場合、その誤った列数へブラウザ側の再配分を強制してしまい、かえってレイアウトを歪める副作用があったと判明（`columnCount`は撤去した）。
- 本文中の空行（`<p><br></p>`、シーン区切り等で頻出）はテキストノードを持たないため、テキストのみを走査する実測方式では見落とされ、そこを誤ってページ境界と誤検出する原因にもなっていた（`<p>`要素自体の`getBoundingClientRect()`も併せて見るよう修正済み、ただし根本問題の解決には至らず）。

**次にやるなら**: `column-gap`に頼らないアーキテクチャへの転換を検討する。例えば、CSS多段組をやめて本文をJS側で実際に行単位に分割し、固定数の行ごとに明示的な「ページ」DOM要素（別々の`<div>`等）を生成してJSで管理する方式（本のページネーションライブラリでよく使われる手法）。CSS任せの`columns`レイアウトのブラウザ内部実装に依存しない分、実装コストは上がるが確実性は高い。

**採用しなかった案**: さらに別のCSS調整を試し続ける案 → 同種の調整（列幅・余白・列数の指定方法の変更）を5回試して全て同じ壁に当たったため、CSS `columns`ベースのアプローチ自体の限界と判断し、これ以上は同じ延長線上での試行を打ち切った。

## 2026-07-20: 縦書きページ送りを「CSS columnsを一切使わない」方式で再実装し、解消

**決定**: 上記の一連の試行で分かった通り、`vertical-rl` + CSS多段組(`columns`)の組み合わせ自体がChromiumで信頼できないため、columnsを完全に廃止した。スクロールモードと同じ「自然な1本の連続レイアウト」のまま本文をレンダリングし、実測した各行の占有範囲(`left`〜`right`、`Range.getClientRects()`で実測)を画面幅に収まる行数ごとにグルーピングしてページを構成する。

**追加で判明した重要な点**: 単に実測ベースにしただけでは不十分だった。行の占有幅は離散的なため、各ページのグループ幅は画面幅ぴったりにはならない（通常やや狭い）。この差分（スラック）を「scrollLeftをページ幅ぶんずつ動かす」固定ステップ方式や、「余りを片側に寄せる」「余りを両側に均等配分（中央寄せ）」する方式で吸収しようとしたが、いずれも数px〜数十px単位で隣接ページの行が見切れる不具合が再現した（Playwrightで文字ごとの`getClientRects()`を実測し、ビューポート境界をまたぐ文字を自動検出する回帰テストスクリプトで複数パターンを検証して判明）。

根本原因: 行同士がゼロギャップで密に並んでいる（column-gapのような構造的な余白が無い）自然なレイアウトでは、固定幅(画面幅)のビューポートが「グループの内容ぴったり」に一致することは基本的にない。この不一致分は必ずどちらかの隣接行の領域に食い込む。

**採用した解決策**: ページごとに「スクロールしてクリップする領域」自体の幅を、画面幅固定ではなく**そのページのグループ幅ちょうど**に動的に変更し、`margin: 0 auto`で画面内に中央寄せして表示する（フロントエンド実装は`vPagerRef`という内側コンテナのCSS `width`をページ送りのたびに書き換える）。クリップ領域の外側には隣接ページの内容がそもそも存在しないため、見切れが原理的に起こり得ない。タップ判定（ページめくり方向）は画面全幅の外側コンテナで行うため、UXは画面幅固定のときと変わらない。

フォント・行間・画面幅を変えた6パターン（14px/16px/18px/22px/24px/12px × 各種line-height・viewport幅）でPlaywrightの自動検証スクリプトを実行し、いずれも文字の見切れゼロを確認した。

**副産物**: 見た目のトレードオフとして、ページごとに実際に表示される横幅がわずかに変動する（内容量に応じて左右の余白が変わる）。CSS columnsのcolumn-gapを使った横書き版のような「どのページも画面ぴったりで両端に均一な余白」という体裁は再現できないが、機能面（文字が絶対に見切れない）を優先した。

**内容**: Phase2で生成した`frontend`は`eslint-plugin-react-hooks@7.1.1`を使っており、React Compiler向けの新しいルール（`react-hooks/set-state-in-effect`、`react-hooks/purity`等）がデフォルトでエラーになっていた。データ取得のため`useEffect`内で非同期関数を呼びその中で同期的に`setState(true)`するという極めて一般的なパターンが軒並みエラーになる。

## 2026-07-18: 全話一括取得エンドポイント `POST /novels/{novelId}/download` を追加

**決定**: ユーザーが明示的に呼び出した場合に限り、作品の全話本文をレート制限を維持したまま順次取得して一括で返すエンドポイントを追加した（`NovelQueryService.getAllChapterContents`）。話数分のリクエストを`NarouRateLimiter`が引き続き1秒間隔に制御するため、レスポンスは話数に比例して時間がかかる（実測: 15話で約15秒）。本文はサーバーに保存しない（従来方針を維持）。

**背景・理由**: 「なろう本文取得はレート制限付きHTML取得で実装した」の決定で「一括クロール（全話の先読み等）を行わない」としていたが、これはrobots.txtの`Crawl-delay`が求める「リクエスト間隔の遵守」と、要件定義にある「任意作品のオフライン保存」（ユーザーが明示的に全話を保存したい場合の機能）を混同していた。robots.txtはリクエスト総数やページ範囲を制限しておらず、間隔さえ守れば全話取得は禁止されていない。ユーザーからの明示的な指示（2026-07-18「一気に全話とってこれるように実装はできない？」）を受け、レート制限は維持したまま一括取得エンドポイントを追加する形で対応した。「自動・無音での全話先読み」は依然として行わない（`GET /novels/{id}/chapters`は話一覧のみでbodyHtmlは含まない）。

**採用しなかった案**: レート制限を緩めて並列/高速取得する案 → robots.txtのCrawl-delayに反するため不採用。非同期ジョブ化＋進捗通知（SSE等）する案 → 個人利用アプリの規模（既知の作品は数百話程度）では同期レスポンスで十分と判断し、複雑さを避けた。将来長大な作品で問題になった場合は`docs/KNOWN_ISSUES.md`を参照して非同期化を検討する。

## 2026-07-18: リフレッシュトークンはハッシュ化して永続化し、ローテーション＋失効管理を行う

**決定**: アクセストークンはステートレスJWT（30分TTL）、リフレッシュトークンは不透明なランダム文字列（Base64）を発行し、DBには SHA-256 ハッシュのみを保存する。リフレッシュのたびに旧トークンを失効させ新トークンを発行する（ローテーション）。`docs/phase1/er-diagram.md` には存在しない `refresh_tokens` テーブルをPhase3で追加した。

**理由**: 完全ステートレスなリフレッシュトークン（JWT化）にすると、ログアウトやトークン漏洩時に個別に無効化する手段がなくなる。個人利用アプリとはいえ複数デバイスを使うため、最低限の失効機構は持たせるべきと判断した。生トークンをDBに平文保存しないことで、DB漏洩時にもリフレッシュトークンを復元されないようにしている。

**採用しなかった案**: リフレッシュトークンもJWTにする案 → 失効不可能になるため不採用。

## 2026-07-18: ドメイン層のRepositoryインターフェースはSpring Data JpaRepositoryを直接継承する（architecture.mdからの実装上の簡略化）

**理由**: 個人利用规模のアプリでこれらのリポジトリに複数実装（DB以外の永続化手段への差し替え）が生まれる可能性は低く、インターフェース+実装クラスを機械的に分離するだけの層は保守コストに見合わないと判断した（YAGNI）。一方、実際に複数実装が存在し差し替えが本質的な価値を持つ `NovelSiteAdapter`（なろう/カクヨム/ハーメルン/pixiv小説/フォールバック）についてはinfrastructure/adapter配下に実装を分離し、`SiteAdapterRegistry` で解決する設計を維持した。クリーンアーキテクチャの本質（依存性逆転が必要な箇所でのみ抽象化する）は保っている。

**採用しなかった案**: 全リポジトリをドメインインターフェース+infrastructure実装クラスに分離する案 → ボイラープレートが増えるだけで実益がないため不採用。

## 2026-07-18: 本棚の「お気に入り」をステータスと独立した真偽値にする

**決定**: `bookshelf_entries.status`（READING/COMPLETED/READ_LATER）とは別に`is_favorite`という真偽値カラムを設け、直交する概念として扱う。

**理由**: 要件文の「読書中/お気に入り/読了/あとで読む/更新あり」をそのまま単一の排他ステータスにすると「読書中かつお気に入り」を表現できない。Kindle等の実際の電子書籍リーダーでも「お気に入り」はステータスでなくフラグ的に扱われることが多く、UXとして自然。

**採用しなかった案**: 5つを単純な排他enumにする案 → 表現力不足のため不採用。

## 2026-07-18: 「更新あり」はユーザー操作ではなく計算値として扱う

**決定**: `has_update`は`novels.latest_known_chapter_no`と`reading_positions.last_read_chapter_no`の差分から導出する。専用のステータス値としてDBに保存しない。

**理由**: 「更新あり」は本来ユーザーが手動設定するものではなく、システムが検知した状態。ステータスとして永続化すると、更新確認バッチとの二重管理になり不整合の原因になる。

## 2026-07-18: 技術スタック・開発フェーズはユーザー指定のまま採用

**決定**: Frontend: Next.js + TypeScript + Tailwind CSS + PWA。Backend: Spring Boot + Java 21 + PostgreSQL。Infrastructure: Docker Compose（将来ConoHa VPSへそのままデプロイ可能な構成）。Phase1〜6の順序・各フェーズ末レビューゲートもユーザー指定のまま採用。

**理由**: プロジェクト概要でユーザーが明示的に指定。
